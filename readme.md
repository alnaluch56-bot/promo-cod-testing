# Тест-дизайн: Валидация промокода

## 1. Краткое описание функции и её правил валидации
Функция `validate_promo_code(promo_code)` предназначена для проверки строки промокода. Функция возвращает `true`, если строка соответствует всем четырём правилам: её длина находится в диапазоне от 6 до 12 символов включительно, она состоит только из латинских букв и цифр, содержит как минимум одну цифру, и при этом строка не совпадает (без учёта регистра) с запрещёнными значениями из чёрного списка: "TEST", "FREE", "INVALID". В противном случае функция возвращает `false`.

## 2. Классы эквивалентности

### Валидные классы (ожидаемый результат — true):
1. Строки длиной 6–12 символов, состоящие из букв и цифр, с наличием цифры: `abc123`, `User2024`.
2. Строки минимальной допустимой длины (ровно 6 символов): `a1b2c3`.
3. Строки максимальной допустимой длины (ровно 12 символов): `User20241234`.

### Невалидные классы (ожидаемый результат — false):
1. Слишком короткие строки (менее 6 символов): `abc1`, `a1`.
2. Слишком длинные строки (более 12 символов): `abcdefgh12345`.
3. Строки без цифр: `abcdef`, `HelloWorld`.
4. Строки, содержащие спецсимволы (не буквы и не цифры): `abc!123`, `user@2024`.
5. Строки из чёрного списка в любом регистре: `TEST`, `test`, `Free`, `invalid`.

## 5. Использование документации при работе с Git
Данный файл README.md является отправной точкой для команды при работе с тестами валидации. В систему контроля версий (Git) логично фиксировать изменения отдельными коммитами: например, один коммит для добавления новых классов эквивалентности, второй — для обновления граничных значений, третий — для правок таблицы решений. Такой подход позволяет при проведении код-ревью быстро понять, какие именно тесты были затронуты изменениями. Если логика функции поменяется, разработчик сможет открыть этот файл, свериться с таблицей решений и оперативно обновить нужные тест-кейсы в файле `test_cases.txt`.
